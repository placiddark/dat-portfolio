Darren Thompson / Independent technology case study

Bug bounty research with a source trail.

HELM grew out of my own bug bounty research. I designed the concept around a practical question. How can agents help a researcher make sense of program rules and evidence while keeping every decision open to review?

Explore the research workflow See the Helkhem53 concept

Research foundation

The program rules shape the work.

A bug bounty program’s scope defines which assets a researcher may test and which practices the program allows. Its policy can also exclude entire classes of systems and specify how to report a finding. I wanted a research record that kept those terms tied to the program’s own wording so I could compare programs and revisit a decision later.

That led to a handoff design. A policy note carries its source and review date. An observation carries the researcher’s account. An impact statement points back to evidence. Each record has a different job, and the language makes that difference visible.

Core technology

How the console holds the work together.

The original HELM dashboard design used HTML, CSS and JavaScript for its panel layout, form and controls. The agent workflow builds on the same research record. A program note, a draft and a triage reply each belong to the record the researcher is reviewing.

Structured intake

The intake form captures the program, finding category and status. The research workflow adds a source reference and room for open questions so an agent has context when it gets the record.

Pipeline and review gates

The pipeline tracks where each report stands. A gate identifies the decision that still needs a person, such as confirmation of scope or an impact claim that needs stronger support.

Alerts and triage history

The dashboard design includes an alert feed and a place for triage replies. The researcher can return to the report with the program notes, draft and reviewer response in view.

Proposed architecture

What each agent hands off.

The concept gives agents bounded jobs on public program documents and researcher-supplied records. Each handoff carries the source, the work completed and any open question. The researcher resolves scope questions and approves the report.

Program research

Policy reader

Summarises public program terms and returns the source passage beside each scope or disclosure note. Ambiguous terms go to the researcher for a decision.

Evidence review

Evidence editor

Organises notes the researcher provides. It marks which statements describe direct observations and which express an interpretation, then identifies claims that lack a reference.

Disclosure drafting

Report assistant

Turns reviewed notes into a draft summary and an impact statement. It preserves open questions and returns the draft to the researcher for approval.

Helkhem53 / Swarm concept

Thirty agents need a shared language.

My Helkhem53 concept brought a 30-agent swarm into HELM’s design. I describe its design space as “331,000 actualizable.” This case study illustrates the concept through document review, where agents give the researcher different editorial perspectives on the same record.

Language Soul

The shared vocabulary gives every role a way to distinguish a source quote, an interpretation and a decision. That distinction carries through to the labels a researcher sees in the console.

Persona Archetypes

Each role reads with a different question in mind. The policy reader asks what the source says. The evidence editor asks what the record supports. The report assistant asks what a reviewer needs to understand the claim.

Thought Clouds

A thought cloud gives the open questions around a record a place to sit together. One reading may point to an exclusion. Another may flag a missing source passage. The researcher can see both before deciding what the record should say.

“Scope needs confirmation” is an example of how those perspectives come back to the researcher. The status names the decision the person needs to make. The next line tells them where to look.

Prompt design and interface copy

The writing defines the next decision.

I brought the same question I ask when I write a landing page CTA into HELM. What should happen next, and what does the reader need to know first? That question shaped the agent briefs and the language the console uses when a decision comes back to the researcher.

Agent instruction

Make uncertainty visible

“Cite the program passage for each scope note. If the passage leaves eligibility unclear, mark the scope unresolved and quote the wording that needs review.”

The instruction gives the policy reader a concrete way to handle ambiguity and gives the researcher the text needed to resolve it.

Interface guidance

Give the next action a name

Scope needs confirmation.

Open the source policy and record your decision.

Review scope

The status explains why the record needs attention. The button names the task the researcher is about to open.

Editorial guidance

Write to the evidence

“Describe the impact the evidence supports. Link each claim to a researcher note. Mark any claim that still needs support.”

The report brief puts the reviewer’s first question into the drafting process. What can I verify from this report?

My contribution

From research habit to product specification.

I used my bug bounty research to define what HELM should carry from one stage to the next. I designed the roles and handoffs for this showcase, then wrote the agent instructions, status messages and review prompts that express those decisions.

The case study presents a proposed workflow and example copy. The console illustrates what a researcher would see when an agent reaches the limit of what the source can support.
